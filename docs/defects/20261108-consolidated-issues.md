## 二、两条最重要的结构性缺陷

### 1. 验收判据由实现方写（D-7）

AgentLine 协议写的是 **designer 产出 `design.md` + `acceptance.md`**，但实测中 `acceptance.md` 在 dev 轮次里被反复重写，判据随之漂移。

后果：

- dev 写不动实现时改判据，而不是改代码
- 判据绑定实现细节（测试标题），功能通过、验收变红
- T-013 因此耗掉 4 轮 + 一次任务拆分

**建议**：`acceptance.md` 移出 dev 的 write_scope；改动须走 amendment 请求。

### 2. worktree 与 main 之间没有修复回灌（D-3 的延伸）

实测遇到三种形态，全部导致"改了等于没改"：

| 形态 | 现象 |
|---|---|
| brief 未提交 | 设计师报告"没有 brief.md" |
| 扩权只提交到 main | 已存在的 worktree 看不到，合并时被判越界 |
| 修复只提交到 main | 评审反复报已修好的问题，导致 4 轮空转 |

**建议**：任务元数据（brief/state/logs）不依赖 git 跟踪；或 `flow` 启动时同步 main。

## 三、按优先级排期的建议

| 优先级 | 事项 | 预期收益 |
|---|---|---|
| **P0** | `check-acceptance` 守卫：命令数为 0 / 绑定测试标题 / 缺 `AC-xxx OK` 三项检查 | 省 4 次 CI 失败（约 60 分钟/批） |
| **P0** | `acceptance.md` 归属改到 designer，移出 dev 写域 | 消除判据漂移 |
| **P1** | `failure.json`：聚合 blocked_reason、失败 AC、最后三次调用、候选切换次数 | 归因从"人工下钻四层"变成"读一个文件" |
| **P1** | 验收断言失败时必须输出子进程 stdout/stderr（D-8） | T-013 排查省 3 轮 |
| **P1** | `flow` 启动前检查 git 可用性与 `/mnt` 污染（D-9） | 避免整仓 git 失效 |
| **P2** | `scope` 子命令：越界申请走正式流程 | 替代"改图 + 塞 note"旁路 |
| **P2** | stall 拆分首字节/中途静默，并记录等待时长（D-5） | 单次 stall 从 15 分钟降到 3 分钟 |
| **P2** | Blueprint JSON 提取改用反向解析（D-1） | 避免整轮设计作废 |

## 四、四个可复用的操作结论

1. **重试不是策略，改变假设才是**：同一 AC 连续 3 轮失败 → 缩小范围或拆任务（T-013 已验证）
2. **分支与 main 分叉且冲突复杂时，重建优于解冲突**：删 worktree 从 main 重建（T-008、T-013 各用过一次，都一次通过）
3. **读别人的报告不如跑一次命令**：T-013 的根因（配置路径 → 测试文件缺失 → 测试标题不匹配）全部靠手工下钻才发现
4. **判据要黑盒**：只断言退出码/输出/文件状态，不断言测试标题、函数名、行号、其他任务状态
