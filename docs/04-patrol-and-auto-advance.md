# 巡检（Patrol）：无人值守推进的运维协议

> 本文记录 2026-11-07 夜间在 `dsh-CLIWorker` 上实际跑通的一套"巡检"做法，建议作为调度器/插件的一等能力实现，而不是靠人肉值守。
> 来源：M1 九个任务、约 8 小时连续推进中的真实故障与处置记录。

## 1. 为什么需要巡检

单个 `flow` 只在**进程内**推进：它不会发现"任务在排队却显示已实现"、"git 配置被上游写坏"、"验收脚本格式不对导致 CI 0 条命令"这类**进程外**问题。夜间实测中，这类问题占了总耗时的 55%。

巡检解决的是：**谁在任务之间做判断**。

## 2. 五项前置体检（不等任务 blocked 才看）

每轮巡检先做这五项，发现问题直接修，**不要等它变成失败**：

| # | 体检 | 检查方式 | 为什么必须先做 |
|---|---|---|---|
| 1 | 跨任务耦合断言 | grep `test/` 中是否写死了其他任务的产物状态（`merged.acs['AC-0xx'] === 'planned'`、固定计数） | 后续任务补分片时必然变红，且修它不在任何任务写域内 → 任务级死锁 |
| 2 | 主工作区分支 | `git rev-parse --abbrev-ref HEAD` 必须为 `main` | 合并后可能停在 `task/xxx`；也可能被 WSL agent 写入 `/mnt/c/...` 导致 git 全面失效 |
| 3 | 槽位真实性 | 用**进程列表**核对，而不是只读 `state.json` | 状态说 `reviewable` 但无进程 = 排队或被遗弃；也可能是串行启动被误当并行 |
| 4 | 验收可解析性 | 每个 worktree 的 `acceptance.md` 是否含 `## AC-xxx` 标题与 `- 命令:` 行 | runner 解析失败时只给 `exit 2` 且不生成 `ci-results.json`，"没跑"与"全挂"不可区分 |
| 5 | write_scope 陈旧 | 扩权/修复提交到 main 后，活跃 worktree 是否同步 | worktree 只含已提交内容；只改 main 等于没改 |

## 3. 五件套：失败归因的固定入口

任何 flow 结束，**先读这五样再下结论**，不要依赖人工转述：

| 文件 | 用途 |
|---|---|
| `state.json` | `status`、`blocked_reason`、轮次 |
| `notice.json` | CLI 自报的阻塞摘要（对应插件要做的"问题优先页"） |
| `impl.md` | 开发者自述：做了什么、哪里被卡住 |
| `ci-results.json` | 失败 AC 列表与原始输出；**文件不存在 = runner 解析失败** |
| `run.json` | 模型、耗时、`error`、候选切换次数 |

辅助：`handoff/*.md`（换模型时的交班单）、`logs/<role>-<round>-<candidate>.log`。

## 4. 判定表

| 现象 | 归类 | 处置 |
|---|---|---|
| `blocked_reason = ci_failed` 且**无** `ci-results.json` | 验收脚本格式 | 按 runner 契约整份重写 acceptance，不要逐行补 |
| `blocked_reason = ci_failed` 且有结果 | 产品代码错 | 带失败清单打回 dev，要求本地跑 `check-fast` 自证 |
| `awaiting_human` + `attention.json` | 写域不足/歧义 | 按选项裁决；单文件且不改变对外契约 → 直接批准并记录 |
| `blocked_reason = rate_limit` | 额度耗尽 | 切模型链，保 design、降 review |
| `blocked_reason = stall` | 活性超时 | 同模型先重试一次，仍 stall 才换候选 |
| `merge` 报 `Aborting` | 主工作区有未跟踪残留 | 清理 `?? .collab/tasks/<id>/` 后再合并 |
| git 报 `Invalid path '/mnt'` | 跨平台 agent 污染 | 清 `.git/config` 中的 `worktree = /mnt/...`，并把 WSL provider 移出角色链 |

## 5. 越权与扩权

`write_scope` 不是沙箱，只是账本。实测中 **3 个任务**因写域不足而停摆（005/006/007），全部是单文件、边界清晰的场景。

建议插件提供正式的 `scope` 流程：

```
dev 提交越界请求（文件、原因、diff 规模）
  → 巡检/操作者批准
  → 写入 inputs.jsonl 与 state
  → 同步到 main 与所有活跃 worktree（关键）
```

当前只能靠"改 task-graph + 塞 note"的旁路，不可审计、也不可复用。

## 6. 合并授权

巡检可以吞掉逐任务的人工放行，但**必须留下授权原文**：

- 低档（`merge_risk = low`）：预授权 `merge --grant`
- confirm 档：`merge --permission "<用户原话>"`
- 每次合并记录里写明 `permission_kind` 与用户原话

## 7. 升级阈值（只在四种情况打断人）

1. 同一任务连续 **3 次同类失败**（说明方案本身错了，不是执行问题）
2. 需要改**契约/接口**
3. **凭据或额度**硬性耗尽
4. 需要**产品决策**（范围、优先级、取舍）

其余一律自行推进 —— 这正是巡检存在的意义。

## 8. 建议的插件实现

| 能力 | 形式 |
|---|---|
| 巡检循环 | 定时任务（实测 10 分钟一次足够），或插件内 `setInterval` |
| 五项体检 | 一个 `patrol check` 子命令，输出结构化 JSON |
| 五件套聚合 | 落到 `<task>/failure.json`：`blocked_reason`、失败 AC、最后三次调用、候选切换次数 |
| 问题优先页 | 插件 UI 的第一个标签页，CLI 自报问题按严重度排序，可点开证据 |
| 未闭环标记 | 模型自报无法完成但 flow 继续的情况必须持续可见并标红 |
| 自动修复 | 验收格式重写、git 配置修复、扩权同步 —— 建议先做"可自动判定"的三类 |

## 9. 实测收益

| 指标 | 无巡检 | 巡检介入后 |
|---|---|---|
| 任务平均耗时 | 40 min | 仍 40 min，但**失败重试从 4.8 次降到 1 次** |
| 阻塞到恢复 | 需人工发现（数小时） | ≤ 10 min |
| 合并等待 | 每个任务等人 | 0（授权原文留痕） |

## 10. 一句话

**巡检不是"更勤奋地盯着"，而是把"任务之间需要做的判断"变成可执行、可复现的检查项。** 这些判断目前只存在于操作者的脑子里，插件化之后才会随上下文一起不丢失。
